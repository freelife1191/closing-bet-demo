  모듈 잠금이 걸치지 않기 때문이다. 워커 A 가 끝낸 뒤 B 가 잠금을 잡으면 B 의
  `RENAME TO chatbot_memories_legacy` 가 이미 새 스키마인 테이블을 되돌린다.

  **세션과 메모리의 소유자 규칙이 정반대다.** `chatbot_sessions` 는 `owner_id IS NULL` 을
  「레거시, 누구나 접근 가능」으로 쓰고, 메모리의 `owner_id = ''` 는 「공용, 아무에게도
  노출되지 않음」이다. 그래서 `storage_memory_manager.py` 의 정규화 함수를
  `_normalize_memory_owner_id` 로 이름 지어 `storage_sqlite_history.py:288` 의 동명 함수와
  구별했다.

  죽은 코드를 함께 지웠다. `core_command_mixin.py` 의 래퍼 셋(`_render_memory_view`,
  `_handle_memory_write_action`, `_handle_memory_command`)은 바뀐 시그니처를 못 따라가
  호출 즉시 TypeError 를 냈고 저장소 전체에 호출자가 없었다. `core.py` 의 `get_memory`,
  `update_memory`, `clear_memory` 도 마찬가지였다. 삭제한 검사는 하나로,
  `test_save_memories_uses_temp_table_fallback_for_large_snapshot` 가 검사하던 인라인
  `NOT IN` 분기가 사라져 검사 대상이 없어졌다. 임시 테이블 경로는 남은 검사가 덮는다.

  리뷰 지적 셋을 백로그로 세웠다. `[CHAT-021]`(프로필 API 소유자 판정 누락),
  `[CHAT-022]`(워커 간 전체 동기화가 남의 행을 지움), `[CHAT-023]`(공용 캐시 무제한 누적).
  QA 가 새로 찾은 `[CHAT-024]`(낮은 뷰포트에서 버튼이 카드를 가림)도 함께 올렸다.

  QA 를 돌리기 전에 gunicorn 워커를 `kill -HUP` 으로 재기동해야 했다. `--reload` 없이 돌기
  때문에 워커가 17:59 에 로드한 옛 코드를 들고 있었고, 그대로 검사했으면 새 코드를 한 번도
  거치지 않은 채 통과 보고를 낼 뻔했다.
