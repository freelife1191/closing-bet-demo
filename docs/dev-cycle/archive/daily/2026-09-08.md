- 메모: `os.chmod` 를 쓰기 뒤에 두면 기존 0644 파일에서도 새 시크릿이 0644 아래 쓰이는 창이 남는다. `open(w)` 가 이미 잘라낸 뒤라 `os.fchmod` 를 블록 맨 앞에 두면 그 창이 없다(실측).
- 메모: 모드 변경은 **이미 열린 파일 기술자를 회수하지 않는다.** 0644 이던 동안 열어 둔 기술자는 같은 inode 에 이어 쓰이는 값을 계속 읽는다. 보안 리뷰와 Codex 가 독립적으로 같은 지적을 냈다. 근본 해법은 새 inode + `os.replace` 이며 `[INFRA-050]` 이 맡는다.
- 메모: `atomic_write_text` 를 쓰는 다른 `.env` 쓰기 경로는 `NamedTemporaryFile`(0600) + `os.replace` 라 **이미 0600 을 남긴다.** 「일관성」을 이유로 함께 고치지 않았고 그 전제를 QA S-7 로 확인했다.
- 메모: **`.env` 를 0600 으로 좁혀도 같은 값이 `frontend/.next` 에서 읽혔다.** Turbopack 의 FileSystem Cache 가 프로세스 환경을 직렬화하며, `restart_all.sh` 의 심볼릭 링크 때문에 백엔드 전용 시크릿까지 그 환경에 오른다. 실측으로 키 16개가 파일 3,222개에 평문·0644 로 있었다. 캐시는 실행마다 새로 만들어져 파일 모드로 막을 수 없어 `chmod 700 frontend/.next` 로 순회를 끊었다.
- 메모: 검사가 **최종 상태만 재면 순서 회귀를 놓친다.** `os.fchmod` 를 블록 밖 `os.chmod` 로 옮겨도 최종 모드와 내용이 같아 통과한다. 좁히는 시점의 파일 크기를 재는 검사를 더했고, 돌연변이 둘로 그 검사만 실패하는 것을 확인했다.
- 메모: 워커가 `--reload` 없이 도는 탓에 **화면 저장 경로는 다음 재기동 전까지 옛 코드를 쓴다.** 5501 워커는 00:39 기동, 변경은 07:37 이었다. QA 를 하네스로 설계한 이유이며 저장소 learning `gunicorn-needs-hup-before-qa` 와 같은 사실이다.
- 메모: 「파일 소유자와 워커가 같으니 `fchmod` 는 실패하지 않는다」는 단정을 적었다가 적대적 리뷰가 반례를 냈다. macOS `chflags uchg` 는 소유자가 스스로 걸 수 있고, POSIX 권한 비트를 지원하지 않는 마운트에서는 언제나 실패한다. 계정 불일치는 실패 원인 가운데 하나일 뿐이다.
