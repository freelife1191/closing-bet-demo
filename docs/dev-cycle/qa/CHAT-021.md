# [CHAT-021] 챗봇 프로필 API 가 소유자 판정 없이 한 벌을 공유한다 — QA 시나리오

- 대상 화면: http://localhost:3500/chatbot
- 구성 근거: /qa-only 리포트 (.gstack/qa-reports/qa-report-localhost-3500-2026-09-06.md)
  + 이번 사이클의 변경 다섯 파일
- 구성 2026-09-06 07:05 | 실행 2026-09-06 07:07

## 검사 전 준비

gunicorn 은 `--reload` 없이 돌고 있어서 워커가 기동 시점의 코드를 들고 있다. 구현 파일을
고친 뒤에는 `kill -HUP <마스터 PID>` 로 워커를 재기동해야 이 시나리오가 새 코드를 검사한다.
이번 구성 시점에는 마스터 8939 에 HUP 을 보내 워커를 83250 과 83251 로 새로 띄웠고,
`GET /api/kr/market-gate` 가 200 을 돌려주는 것으로 생존을 확인했다.

## 시나리오

### S-1. 챗봇 화면이 기본 프로필 이름을 그린다 (회귀)
- 조작: `http://localhost:3500/chatbot` 을 연다. 화면 가운데의 인사말과 우측 상단
  아바타의 글자를 읽는다.
- 기대: 인사말이 `안녕하세요, 흑기사님` 이고 아바타에 `흑기` 가 표시된다. 이 값은
  브라우저 `localStorage` 에 `user_profile` 키가 없을 때 프런트엔드가 쓰는 폴백
  기본값이므로, 서버 변경과 무관하게 종전과 같아야 한다.
- 결과: 통과. 헤딩 `안녕하세요, 흑기사님`, 아바타 텍스트 `흑기`, 아바타 title `흑기사`, `localStorage` 의 `user_profile` 은 없음.

### S-2. 소유자를 몰라도 프로필 조회가 막히지 않는다 (회귀)
- 조작: 헤더 없이 `GET /api/kr/chatbot/profile` 을 호출한다.
- 기대: HTTP 200 과 함께
  `{"profile": {"name": "흑기사", "persona": "주식 투자를 배우고 있는 열정적인 투자자"}}`
  가 나온다. 조회는 소유자를 몰라도 거절하지 않고 기본 프로필을 돌려주도록 구현했다.
- 결과: 통과. HTTP 200, `{"name": "흑기사", "persona": "주식 투자를 배우고 있는 열정적인 투자자"}`.

### S-3. 소유자 헤더가 있어도 저장된 것이 없으면 기본 프로필이 나온다 (회귀)
- 조작: `X-Session-Id: anon_qa_probe_a` 헤더를 붙여
  `GET /api/kr/chatbot/profile` 을 호출한다. 이어서 `anon_qa_probe_b` 로 한 번 더
  호출한다.
- 기대: 두 호출 모두 HTTP 200 과 S-2 와 완전히 같은 기본 프로필을 돌려준다. 저장소에
  어느 소유자의 `user_profile` 행도 없기 때문이다.
- 결과: 통과. 두 소유자 모두 HTTP 200 과 S-2 와 같은 기본 프로필.

### S-4. 이름이 빠진 저장 요청을 거절한다 (회귀)
- 조작: `X-Session-Id` 헤더를 붙이고 본문에 `{"persona": "검사용"}` 만 담아
  `POST /api/kr/chatbot/profile` 을 호출한다.
- 기대: HTTP 400 과 `{"error": "Name is required"}` 가 나오고 저장은 일어나지 않는다.
- 결과: 통과. HTTP 400, `{"error": "Name is required"}`. 저장소 행 수가 늘지 않음(S-8 에서 확인).

### S-5. 소유자를 알 수 없는 저장 요청을 거절한다 (이번 변경의 핵심)
- 조작: `X-Session-Id` 헤더를 빼고 본문에 `{"name": "검사", "persona": "검사용"}` 을
  담아 `POST /api/kr/chatbot/profile` 을 호출한다.
- 기대: HTTP 400 과 `{"error": "Session is required"}` 가 나온다. 이 응답이 이번
  사이클에서 새로 생긴 것이다. 종전에는 소유자 판정 없이 저장되어 한 사용자가 적은
  이름과 페르소나가 다른 사용자의 조회에 그대로 실렸다.
- 결과: 통과. HTTP 400, `{"error": "Session is required"}`.

### S-6. Next.js 프록시를 거쳐도 같은 판정이 나온다 (인접)
- 조작: 브라우저에서 `/api/kr/chatbot/profile` 로 S-2 와 S-5 를 각각 호출한다.
  `frontend/next.config.js` 의 rewrite 를 거치는 경로다.
- 기대: 직접 호출과 같은 결과가 나온다. 조회는 200 과 기본 프로필, 소유자 없는 저장은
  400 과 `Session is required` 다.
- 결과: 통과. 프록시 경유 조회는 HTTP 200 과 기본 프로필, 소유자 없는 저장은 HTTP 400 과 `Session is required`. 직접 호출과 같다.

### S-7. 설정 모달의 프로필 절이 세 값을 그린다 (인접)
- 조작: `/chatbot` 에서 우측 상단 아바타를 눌러 설정 모달을 연다. 「일반」 탭의 프로필
  절에 있는 세 입력을 읽고 「취소」로 닫는다. **「저장」 버튼은 누르지 않는다.** 이번
  변경으로 그 버튼이 서버에 실제 저장 요청을 보내게 되었다.
- 기대: 이름 `흑기사`, 이메일 `user@example.com`, 직무 콤보박스 `엔지니어링` 이
  선택되어 있다. 「무료 사용량 상태」에 `✨ 무료 10회 AI 사용 가능` 이 표시된다.
- 결과: 통과. 이름 `흑기사`, 이메일 `user@example.com`, 직무 `엔지니어링`, 무료 사용량 `무료 10회 AI 사용 가능`. 「취소」로 닫으니 프로필 필드가 사라졌다.

### S-8. 저장소에 프로필 행이 생기지 않는다 (회귀)
- 조작: `data/chatbot_storage.db` 를 **읽기 전용**(`file:...?mode=ro`)으로 열어
  `chatbot_memories` 의 행 목록을 읽는다.
- 기대: 공용(`owner_id = ''`)에 `daily_suggestions_default_empty` 와 `interest` 두 행만
  있고 `user_profile` 행은 어느 소유자에게도 없다. 위 시나리오의 저장 요청은 모두
  400 으로 거절되므로 새 행이 생기지 않아야 한다.
- 결과: 통과. 공용(`owner_id = ''`)에 `daily_suggestions_default_empty`(724바이트)와 `interest`(6바이트) 두 행뿐이고 `user_profile` 행은 0건. 전체 2행으로 검사 전과 같다.

### S-9. 화면이 콘솔 오류 없이 뜬다 (인접)
- 조작: `/chatbot` 을 열고 설정 모달을 열었다 닫은 뒤 브라우저 콘솔의 오류를 읽는다.
- 기대: 화면이 만든 오류가 없다. 검사자가 S-4 와 S-5 에서 직접 보낸 400 응답은
  콘솔에 기록되지만 화면이 만든 것이 아니므로 실패로 세지 않는다.
- 결과: 통과. 화면이 만든 콘솔 오류는 없다. 기록된 400 세 건은 모두 검사자가 S-4·S-5·S-6 에서 직접 보낸 요청이다.

## 검사에서 제외한 조작

- 챗봇 메시지 전송 일체. 「보내기」 버튼, 입력창 Enter, 추천 질문 카드 넷, 하단 빠른
  조회 버튼 다섯, 답변 아래 추천 후속 질문이 모두 실제 Gemini 호출과 유료 쿼터 차감을
  일으킨다.
- 슬래시 명령 `/help`, `/status`, `/memory view`, `/clear`, `/clear all`. 무료 사용량을
  차감하며, 특히 `/clear all` 은 이번 변경 이후 요청자의 프로필까지 지운다.
- 설정 모달의 프로필 「저장」 버튼. 누르면 그 브라우저 세션의 프로필이 실제로 저장된다.
- 설정 모달 「알림 센터」 탭의 「테스트 발송」 버튼 셋과 「API & 기능」 탭의 삭제·저장
  버튼. 앞의 것은 실제 발송을, 뒤의 것은 서버 환경 변수 변경을 일으킨다.
- `GET /api/kr/chatbot/suggestions`. 캐시가 비면 Gemini 를 부른다.
