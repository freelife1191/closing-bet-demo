## 사전 조건

**워커가 새 코드를 들고 있어야 한다.** 이 저장소의 gunicorn 은 `--reload` 없이 뜨므로
파이썬을 고친 뒤 재기동하지 않으면 옛 코드가 그대로 응답한다. 2026-09-05 에 남긴
`gunicorn-needs-hup-before-qa` 학습이 그것이고, 이번 라운드에서 그 확인을 건너뛴 탓에
아래 「사고 기록」의 자료 손실이 났다.

    실행 전 확인: ps -o pid,lstart -p $(pgrep -f "gunicorn.*flask_app" | head -1)
    기준: 워커 기동 시각 > 마지막 소스 수정 시각
    현재: 워커 2026-09-07 16:41:12 기동. 소스 최종 수정 16:4x. 조건 충족.

**`.env` 를 건드리지 않는다.** 아래 시나리오의 POST 는 전부 「허용 목록 밖 키만 담은
요청」이거나 「빈 본문」이다. `update_env_file` 은 필터링 후 남는 키가 없으면 파일을 열지
않고 돌아가므로 파일이 바뀌지 않는다. 시나리오 전후로 SHA-256 을 대조해 그것을 증명한다.

    기준 해시: a199feaf799bfe8dad4ef3ab6cc296aee5f7dd961787fa1a7d81d84d06410f6d

**토큰은 화면에 출력하지 않는다.** `curl` 에 넘길 때 셸 변수로만 다루고
`TOKEN=$(grep '^ADMIN_API_TOKEN=' .env | cut -d= -f2-)` 형태로 읽는다. 응답 본문을 볼 때도
`ADMIN_API_TOKEN` 은 허용 목록에 없어 애초에 실리지 않는다.

| 요청 | 기대 |
|---|---|

**우회 경로 (Next 경유, `http://127.0.0.1:3500`)**

| 요청 | 기대 |
|---|---|

| `GET /api/system%2Fenv` (`--path-as-is`, 세션 없음) | 403 — rewrite 를 타고 Flask 에 닿지만 토큰 검사에 걸린다 |

두 번째 줄이 이번 설계의 근거다. rewrite 제외만 믿었다면 이 경로로 `.env` 가 그대로
나갔다. 계획 검토와 보안 리뷰가 각각 지적했고 보안 리뷰가 실측으로 확인했다.

**화면 (비로그인 = 비관리자)**

| 확인 | 기대 |

| 사이드바에서 설정 모달을 연다 | 열린다 |
| 「일반」 탭 | 보인다 |
| 「API & 기능」·「알림 센터」·「시스템」 탭 | 보이지 않는다 |
| 「설정」 그룹 라벨 | 보이지 않는다 |
| 네트워크에 `/api/system/env` 요청 | 없다 |

관리자 화면은 NextAuth 구글 세션이 필요하고 내장 브라우저에는 그 세션이 없다. 그래서
11·12 는 비관리자 상태만 실측했다. 관리자 경로는

### 실행 중 겪은 것

**워커가 옛 코드를 들고 있어 5·7 이 한 번 실패했다.** 마스킹 임계값을 고친 시각이
16:43:51 인데 워커는 16:41:12 기동이었다. `SMTP_HOST` 가 마스킹되고 `SMTP_PASSWORD` 가
앞뒤를 남긴 상태로 나왔다. 재기동(16:48:23) 후 둘 다 기대대로 바뀌었다. 이 문서 첫머리에
적어 둔 `gunicorn-needs-hup-before-qa` 학습을 적어 놓고도 같은 자리에 걸렸다.

**11·12 는 첫 시도에서 hydration 이 되지 않아 실행하지 못했다가, 나중에 다시 시도해
통과시켰다.** 첫 시도에서는 `Object.keys(button).filter(k => k.startsWith('__react'))`
가 빈 배열이었고 사이드바의 사용자 메뉴 버튼을 눌러도 DOM 이 바뀌지 않았다(클릭 전후
button 수 14 로 동일). 시각을 두고 다시 열었더니 같은 주소에서 `__reactFiber$…` 와
`__reactProps$…` 가 붙어 있었고 클릭이 정상적으로 먹었다. `next dev` 가 첫 요청에서
라우트를 컴파일하는 동안 스크립트가 아직 실행되지 않은 상태를 잡았던 것으로 보인다.
이번 변경과 무관한 일시적 현상이며, 다음에 같은 자리에서 막히면 시간을 두고 한 번 더
열어 보면 된다.

**11 의 실측**: 모달의 탭 버튼 목록이 `["일반"]` 하나였다. 「API & 기능」·「알림 센터」·
「시스템」은 DOM 에 없다. 모달 안의 제목은 프로필·구글 계정·관심 종목·모양 넷으로,
모두 「일반」 탭의 내용이다.

**12 의 실측**: 페이지를 연 시점부터 모달을 닫을 때까지 `/api/system/env` 요청이 없었다.
브라우저 네트워크 로그로 한 번, `performance.getEntriesByType('resource')` 의
`system/env` 항목 수가 0 인 것으로 한 번, 두 경로로 확인했다. 같은 구간에서 실제로 나간
API 요청은 `/api/kr/user/quota` 하나뿐이다. 모달은 「저장」을 누르지 않고 `Escape` 로
닫았다.

10번은 `.env` 를 쓰지 않는 경로임을 앞에서 논증했고, 그럼에도 전후 해시를 대조해
실증한다. 해시가 달라지면 그 자체가 실패다.

13번을 선택으로 두는 이유는 현재 앱이 405 대신 500 을 돌려주기 때문이다. 원인은
`app/__init__.py:254` 의 전역 예외 처리기이며 `[INFRA-017]` 의 범위다. 이번 라운드는
「`DELETE` 로 `.env` 가 초기화되지 않는다」까지만 보장한다.

## 하지 않는 것

- 설정 모달의 「저장」을 누르지 않는다. `AGENTS.md` 가 되돌릴 수 없는 조작으로 지정했다.
- 알림 테스트 발송을 하지 않는다. 실제 메시지가 나간다.
- 챗봇 전송, 재분석, Refresh, 모의투자를 누르지 않는다.
- `data/` 를 쓰지 않는다.
- 관리자 계정으로 로그인하지 않는다. 자격 증명을 다루지 않는다.

## `.env` 자격 증명이 비워진 건 — 경위와 정정

QA 와 직접 관련은 없으나 같은 날 같은 경로에서 벌어진 일이므로 여기에 남긴다.

**사실**: `.env` 의 자격 증명 11개(`OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `SMTP_PASSWORD`,
`GOOGLE_CLIENT_ID` 등)가 16:1x 에는 값이 있었는데 그 뒤 `KEY=` 형태로 비워졌다.
`.env.bak.20260901_084454` 에서 11개 전부 되살렸고, 되돌리기 전 상태는
`.env.bak.20260907_164102` 에 남겼다. 복구 후 56개 키 전부에 값이 있다.

**정정**: 처음에는 보안 리뷰 에이전트가 옛 코드에 `DELETE /api/system/env` 를 보낸 것이
원인이라고 보고했으나 **그것은 틀렸다.** 로그를 읽으면 그 경로의 DELETE 는 두 건뿐이고
(16:34:03 리뷰어, 16:47:48 이 문서의 시나리오 13) 둘 다 `critical_errors.log` 에
`werkzeug.exceptions.MethodNotAllowed` 로 남아 있다. 라우팅 단계에서 거부되어 뷰 함수가
호출되지 않았다. `user_activity.log` 전체에 성공한 DELETE 나 POST 는 없다. 이 경로는
활동 로거의 제외 목록에 없으므로 HTTP 로 실행되었다면 반드시 기록되었을 것이다.

**실행된 함수는 특정했다.** 옛 `FACTORY_RESET_SENSITIVE_KEYS`(커밋 `0767923` 기준 14개)와
비워진 키를 대조하면 완전히 일치한다. 14개 가운데 `.env` 에 실재하고 값이 있던 키가 정확히
11개이고, 비워진 11개가 그것과 같은 집합이다. 대상이 아닌데 비워진 키도, 대상인데 남은
키도 없다. `.env` 에 없던 `ANTHROPIC_API_KEY`·`SLACK_WEBHOOK_URL`·`USER_PROFILE` 셋만
빠진다. 이 정도로 겹치는 것은 `reset_sensitive_env_and_user_data` 가 실제로 실행되었다는
뜻이다. 같은 함수가 `FACTORY_RESET_DELETE_FILES` 도 지우므로 `data/` 의 파일 부재도 함께
설명된다.

**다만 HTTP 로 실행된 것은 아니다.** 활동 로그의 DELETE 두 건은 모두 405 이고 성공한
DELETE·POST 는 없다. 남는 경로는 파이썬에서 그 함수를 직접 부른 것이다. **호출 주체는
확인할 수 없다.** 활동 로거는 HTTP 만 기록하고 `logs/backend.log` 는 `restart_all.sh:80`
이 `>` 로 덮어쓰므로 재기동 이전 기록이 남지 않았다.

즉 「원인 미확인」이 아니라 **「실행된 함수는 특정, 호출 주체는 접근 기록 소실로 재구성
불가」** 가 정확한 기술이다. 이번 라운드가 그 함수와 라우트를 지웠으므로 같은 일이 다시
일어날 경로는 남아 있지 않다.

**남는 교훈 두 가지.** 첫째, 서브에이전트에게 「읽기 전용」이라고만 지시하면 실행 중인
서버에 요청을 보내는 것을 막지 못한다. 둘째, 자료가 사라진 것을 발견했을 때 시각의
근접만으로 인과를 단정하면 안 된다. 활동 로그와 오류 로그를 먼저 읽어야 한다. 둘 다
`AGENTS.md` 의 「되돌릴 수 없는 조작」 절에 적었다.
