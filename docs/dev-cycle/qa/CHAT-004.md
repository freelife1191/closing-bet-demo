## 이 항목이 화면에 닿는 경로

`frontend/src/app/chatbot/page.tsx` 한 파일(1,721줄)을 훅 셋과 메시지 컴포넌트 하나로
나누고, 답변에서 추론과 본문을 가르는 판정 조건 한 줄을 고쳤습니다. 화면에 그려지는 것이
달라지면 안 되는 작업이므로 시나리오는 대부분 회귀 검사입니다.

**고친 한 줄**은 `chatMessageParser.ts` 의 `hasStreamReasoning` 판정입니다. 옮기기 전에는
`typeof streamReasoning === 'string' && streamReasoning.length > 0` 이었고, 지금은 길이
조건을 뺀 `typeof streamReasoning === 'string'` 입니다. 이 조건이 가르는 것은 「이 메시지가
SSE 로 온 것인가」입니다. 세 경로가 이렇게 갈립니다.

| 경로 | `reasoning` 값 | fallback 파서 |
|---|---|---|
| SSE 스트리밍 | `""` 로 초기화된 문자열 | 꺼짐 (백엔드가 이미 나눠 보냄) |
| 히스토리 복원 | 필드 자체가 없음 (`undefined`) | 켜짐 |
| 비스트리밍 JSON 응답 | 필드 자체가 없음 (`undefined`) | 켜짐 |

옛 조건은 추론이 없는 스트리밍 응답(`reasoning` 이 빈 문자열)을 히스토리로 오판정해
fallback 파서를 켰습니다. 그러면 모델이 답변 본문에 「[추론 과정]」이라는 문구를 쓰기만
해도 그 뒤가 통째로 숨었습니다. S-1 과 S-2 가 이 판정을 화면에서 확인하고, 스트리밍 쪽
경로는 아래에 적은 이유로 vitest 가 대신 봅니다.

**챗봇에 메시지를 보내는 조작은 시나리오에 넣지 않았습니다.** 보내기 버튼과 입력 칸의
Enter, 추천 질문 카드 넷, 빠른 조회 버튼 다섯, 추천 후속 질문 셋이 모두 실제 Gemini 호출과
과금을 일으킵니다. `archive-format.md` §8 의 마지막 조항이 이런 조작을 시나리오에서
제외하도록 정하고 있습니다. 그래서 SSE 수신 경로는 화면으로 검사할 수 없고, 대신
`useChatStream.test.ts` 11건이 `applyStreamEvent` 의 여덟 분기를 직접 부르며,
`page.regression-chat-004.test.tsx` 2건이 mock SSE 로 렌더 횟수를 셉니다. S-9 가 그
검사들을 돌립니다.

## 시나리오

### S-1. 히스토리로 복원한 답변에서 추론과 본문이 갈린다 (회귀)
- 조작: `http://localhost:3500/chatbot` 을 연다. 사이드바 「최근 대화」에서
  「삼성전자 최근 주가 흐름 알려줘」를 고른다. 답변 위에 붙는 토글의 개수와 문구를 읽는다.
- 기대: 답변 위에 「생각하는 과정 표시」 토글이 **1개** 나온다. 이 토글은 fallback 파서가
  본문에서 `**[추론 과정]**` 헤더 뒤를 떼어 냈을 때만 렌더된다. 토글이 없으면 판정이
  뒤집혀 추론이 본문에 남았다는 뜻이고, 토글이 둘 이상이면 메시지가 잘못 쪼개졌다는 뜻이다.
- 결과: 통과. 토글이 정확히 1개 나왔고 문구도 「생각하는 과정 표시」였다.

### S-2. 추론 헤더 문구가 답변 본문에 새어 나오지 않는다 (회귀)
- 조작: S-1 의 화면에서 본문 전체 텍스트를 읽어 「[추론 과정]」과 「[최종 답변]」이라는
  문구를 찾는다.
- 기대: 두 문구 모두 화면에 **0건**. 서버가 돌려준 원문에는 `**[추론 과정]**` 이
  들어 있으므로(아래 S-3 에서 확인한다), 화면에 그 문구가 보이면 fallback 파서가 헤더를
  떼어 내지 못한 것이다.
- 결과: 통과. 「[추론 과정]」과 「[최종 답변]」 모두 화면 전체 텍스트에서 0건이었다.

### S-3. 히스토리 API 응답에 `reasoning` 필드가 없다 (회귀)
- 조작: 다음을 실행해 응답의 필드 이름과 본문의 헤더 포함 여부를 읽는다.

      curl -s "http://localhost:5501/api/kr/chatbot/history?session_id=b8191686-3079-4f8a-85d1-594b882548c5"

- 기대: 메시지 **2건**이고 각 메시지의 필드는 `parts`, `role`, `timestamp` **셋뿐**이다.
  `reasoning` 필드가 없다. `role` 이 `model` 인 메시지의 `parts[0]` 은 딕셔너리이고 그
  `text` 는 **1,596자**이며 `**[추론 과정]**` 으로 시작한다. `[최종 답변]` 은 들어 있지
  않다. 이 응답 형태가 이번에 고친 판정 조건의 근거이므로, 여기에 `reasoning` 필드가
  생기면 판정 기준을 다시 세워야 한다.
- 결과: 통과. 메시지 2건이고 두 메시지 모두 필드가 `parts`·`role`·`timestamp` 셋뿐이었다.
  `model` 메시지의 본문은 1,596자이고 `**[추론 과정]**` 으로 시작했으며 `[최종 답변]` 은

### S-5. 새 채팅과 대화 재선택이 서로를 덮어쓰지 않는다 (회귀)
- 조작: 「새 채팅」을 누르고 화면과 `localStorage` 를 읽는다. 이어서 사이드바에서
  「삼성전자 최근 주가 흐름 알려줘」를 다시 고르고 같은 것을 읽는다.
- 기대: 「새 채팅」 직후에는 `chatbot_last_session_id` 가 **`null`** 이고, 인사말이
  「안녕하세요, 흑기사님」(`h1`)과 「무엇을 도와드릴까요?」(`h2`) 두 줄이며, 추천 질문 카드
  **4개**(「마켓게이트 상태와 투자 전략」, 「AI 분석 기반 매수 추천 종목」, 「오늘의 S/A급
  종가베팅 추천」, 「최근 주요 뉴스와 시장 영향」)와 빠른 조회 버튼 **5개**(「시장 현황」,
  「VCP 추천」, 「종가 베팅」, 「뉴스 분석」, 「내 관심종목」)가 나온다. 버튼 총수는 **26개**.
  대화를 다시 고르면 `chatbot_last_session_id` 가
  `b8191686-3079-4f8a-85d1-594b882548c5` 로 돌아오고 추론 토글 1개와 추천 후속 질문

- 결과: 통과(버튼 총수만 사전 조건 차이로 하나 적음). 「새 채팅」 직후
  `chatbot_last_session_id` 가 `null` 이 되었고 `h1` 「안녕하세요, 흑기사님」과 `h2`
  「무엇을 도와드릴까요?」, 추천 카드 4개와 빠른 조회 버튼 5개가 모두 기대한 문구로
  나왔다. 대화를 복원하면 세션 ID 가 돌아오고 토글 1개와 후속 질문 3개가 다시 나왔다.
  버튼 총수만 새 채팅에서 25개, 복원 후 24개로 기대보다 하나씩 적었는데, 사이드바 대화
  목록이 비어 있어 그 항목의 삭제 버튼이 렌더되지 않았기 때문이다(S-7 참조). 대화
  재선택은 사이드바에 항목이 없어 `chatbot_last_session_id` 를 넣고 새로고침하는 경로로
  확인했다.

- 조작: S-1 의 화면에서 답변 아래에 붙은 물음표로 끝나는 버튼을 읽는다. 누르지 않는다.

### S-7. 세션 목록 조회가 인증 헤더를 제대로 싣는다 (회귀)
- 조작: 화면을 새로 불러온 뒤 사이드바 「최근 대화」의 내용을 읽는다.
- 기대: 대화 항목 **1개**가 「삼성전자 최근 주가 흐름 알려줘」라는 제목으로 나온다.
  `getAuthHeaders` 를 `page.tsx` 에서 `chatHelpers.ts` 로 옮겼으므로, 옮기다가 헤더를
  빠뜨렸으면 목록이 비어 「저장된 대화가 없습니다.」가 나온다. 이 검사가 그 회귀를
  붙잡는다. 브라우저의 `localStorage` 에 있는 `browser_session_id` 가 대화를 만든 것과
  같아야 하며, 다른 값이면 목록이 비는 것이 정상이므로 그 경우 이 시나리오는 사전 조건
  미충족으로 처리한다.
- 결과: 사전 조건 미충족. 브라우저의 `browser_session_id` 가
  `anon_dc8003ae-9c4e-4b30-9266-9fedac892770` 로 이 대화를 만든 값과 다르다.
  `/qa-only` 실행 도중 `agent-browser vitals` 가 브라우저 컨텍스트를 대체하면서
  `localStorage` 가 초기화된 결과다. 사이드바에는 「저장된 대화가 없습니다.」가 나왔고,
  이는 소유자가 다른 세션을 목록에서 빼는 정상 동작이다. 헤더가 실제로 실린다는 것은
  서버 쪽으로 확인했다. 같은 소유자 값을 헤더에 실어 `curl` 로 물으면 서버도 0건을
  돌려주므로 화면과 서버의 판정이 일치한다. 이 시나리오가 잡으려던 회귀(옮기다가 헤더를
  통째로 빠뜨림)는 다음 사이클에서 원래 브라우저 세션으로 다시 확인해야 한다.

### S-8. 콘솔과 컴파일과 런타임에 오류가 없다 (회귀)

### S-10. 모바일 폭에서 사이드바가 열리고 대화를 고르면 닫힌다 (인접)
- 조작: 뷰포트를 375×812 로 줄인다. 가로 넘침과 보이는 버튼 수를 읽는다. 햄버거
  버튼(`fas fa-bars`)을 눌러 사이드바를 열고, 「삼성전자 최근 주가 흐름 알려줘」를
  고른 뒤 사이드바 상태를 읽는다. 그다음 뷰포트를 1280×720 으로 되돌린다.
- 기대: 375px 에서 `document.documentElement.scrollWidth` 가 **375** 로 창 너비와 같아
  가로 넘침이 없고, 보이는 버튼 **20개**에 입력 칸이 보인다. 햄버거를 누르면 사이드바가
  덮으며 열리고 대화 항목이 보이며 보이는 버튼이 **25개**로 는다. 대화를 고르면 사이드바가
  **저절로 닫히고** 답변이 나온다. 1280px 으로 되돌리면 보이는 오버레이가 **0개**이고
  가로 넘침이 없으며 버튼이 **25개**로 돌아온다.

  기대값이 새 채팅 화면 기준이었으므로 같은 화면 상태로 맞춰 쟀다. 햄버거를 누르면
  사이드바가 덮으며 열리고 대화 목록 영역이 보였다. 1280px 으로 되돌리면 보이는 오버레이
  0개, 가로 넘침 없음, 버튼 25개로 기대와 같았다. 사이드바가 저절로 닫히는 동작은 대화
  목록이 비어 있어 「새 채팅」을 누르는 경로로 확인했고 누른 뒤 닫혔다. 사이드바를 연
  상태의 버튼만 24개로 기대보다 하나 적었으며 이유는 S-5 와 같다.

## 이월한 발견

`/qa-only` 리포트가 지적한 세 건은 모두 이번 항목이 정한 범위 밖입니다. 이번 작업은
파일을 나누고 판정 조건 한 줄을 고치는 것이었고, 세 건 모두 나누기 전의 `page.tsx` 에
그대로 있던 것이거나 이번에 옮기기만 한 함수의 동작입니다.

- **ISSUE-001** 「답변의 소제목이 빈 `h3` 와 번호 목록으로 쪼개진다」 → `[CHAT-015]` 로
  새로 세웠습니다. 원문의 `### 1. 시장 환경 및 섹터 강도` 가 화면에서는 내용이 빈
  `h3` 하나와 별도의 번호 목록으로 갈라집니다. 원인은 `preprocessMarkdown` 의 치환
  단계일 가능성이 높은데, 이번 사이클은 그 함수를 `chatMessageParser.ts` 로 **옮기기만
  하고 로직을 한 줄도 고치지 않았으므로** 나누기 전에도 같았습니다. 고치려면 정규식
  열두 단계 가운데 어느 것이 제목 줄을 건드리는지 특정하고 그 단계에만 예외를 두어야
  하며, 그 작업은 이번 항목의 체크박스가 정한 범위를 넘습니다.
- **ISSUE-002** 「대화 목록 항목과 상단 탭 둘을 키보드로 조작할 수 없다」 → `[CHAT-007]`
  에 합쳤습니다. 그 항목이 이미 사이드바 대화 항목의 키보드 접근을 다루고 있어서 따로
  세우면 같은 파일을 두 번 건드립니다. 이번에 새로 확인한 것은 상단 탭 「스마트머니봇」과
  「흑기」도 같은 상태(`tabindex`·`role`·`onkeydown` 모두 없음)라는 점이며, 그 사실을
  항목에 덧붙였습니다.
- **ISSUE-003** 「버튼 넷의 이름이 접근성 트리에서 비어 있다」 → 이미 `[CHAT-007]` 에
  들어 있습니다. 이번에도 같은 상태임을 확인했습니다. 보내기(`fa-paper-plane`)와
  햄버거(`fa-bars`)는 `aria-label` 도 `title` 도 없고, 파일 첨부(`fa-plus-circle`)와
  음성 입력(`fa-microphone`)은 `title` 만 있어 접근 가능한 이름으로 계산되지 않습니다.

리포트가 함께 적은 도구 문제 한 건은 애플리케이션의 결함이 아니므로 백로그에 올리지
않았습니다. `agent-browser vitals` 명령이 새 브라우저 컨텍스트를 띄우며 기존 컨텍스트를
통째로 대체해, 열려 있던 탭 셋이 사라지고 `about:blank` 하나만 남았습니다. 주소를 알고
있어 셋 다 다시 열었으나 쿠키가 초기화되어 이 저장소와 무관한 다른 작업의 탭 하나는
로그인 화면으로 되돌아갔습니다. 이후 성능 지표는 `performance.getEntriesByType()` 을
직접 읽어 대신했습니다. 이 사실은 `gstack-learnings-log` 에 함정으로 기록했습니다.
