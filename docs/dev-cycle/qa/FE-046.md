## 시나리오

### S-1. 기동하면 요청 없이도 30일 지난 활동 로그 회전 파일이 지워진다 (핵심)
- 준비: 사본 `logs/` 에 `user_activity.log.2026-02-22`(수정 시각 200일 전), `user_activity.log.2026-09-20`(이름은 최근,
  수정 시각 31일 전), `user_activity.log.2026-01-01`(이름은 오래됨, 수정 시각 2일 전), `other.log.2026-01-01`(400일 전),
  기준 파일 `user_activity.log` 를 모두 0644 로 만든다.
- 조작: 격리 gunicorn 을 띄우고 생존 확인(`/api/kr/market-gate`) 전에 파일 목록을 본다.
- 기대: 앞의 두 파일이 사라지고, `user_activity.log.2026-01-01` 과 `other.log.2026-01-01` 은 남는다. 남은 활동 로그
  회전 파일과 기준 파일은 0600, `other.log.*` 는 0644 그대로다.
- 필수 여부(required): 예
- 실제: 기동 직후 요청 전(10:23:47) `ls -l logs`: `user_activity.log.2026-02-22`·`user_activity.log.2026-09-20` 없음.
  `-rw-------` `user_activity.log`, `-rw-------` `user_activity.log.2026-01-01`, `-rw-r--r--` `other.log.2026-01-01`. 이름은
  최근이지만 31일 전에 수정된 파일이 지워지고 이름은 오래됐지만 2일 전에 수정된 파일이 남아, 기준이 이름이 아니라 수정
  시각임을 확인했다. 기준 파일의 수정 시각이 오늘이라 기동 시 회전은 일어나지 않았다(그 갈래는 단위 테스트
  `test_activity_logger_rotates_and_prunes_a_stale_base_file_on_creation` 이 덮는다)

### S-2. 쓰기로 연 SQLite 파일과 -wal·-shm 이 0600 이 된다 (핵심)
- 준비: 사본 `data/*.db*` 의 권한을 기동 전에 기록한다(원본 복사본이라 0644).
- 조작: S-1 의 기동 뒤 대시보드를 한 번 열고, 사본 `data/*.db*` 권한을 다시 기록한다.
- 기대: 기동과 조회 중 쓰기로 열린 DB 는 본 파일과 -wal·-shm 모두 0600 이다. 0644 로 남은 파일이 있으면 그 DB 가 이번
  구간에서 쓰기로 열리지 않았는지(읽기 전용이거나 열리지 않음) 코드 경로로 확인해 기록한다.
- 필수 여부(required): 예
- 실제: 기동 전 사본의 세 DB 와 `paper_trading.db-wal`·`-shm` 을 모두 0644 로 맞췄다(복사해 온 원본이 이미 0600 이었기
  때문, 위 「원본에 미친 영향」). 기동 직후 `runtime_cache.db` 가 `-rw-------` 로 바뀌었다(기동 때 쓰기로 열림, -wal·-shm 은
  남아 있지 않음). 대시보드 조회와 「모의투자」 모달을 연 뒤에도 `paper_trading.db`·`usage.db` 는 0644 였다. 모달은
  「모의투자는 로그인 후 사용할 수 있습니다」를 보였고 익명 상태에서는 그 DB 를 열지 않는다. 격리 환경에서는 Google 로그인을
  할 수 없어 사본 cwd 에서 `PaperTradingService(auto_start_sync=False)` 를 만들어 실제 서비스 경로로 열었고, 그 뒤
  `paper_trading.db`·`-wal`·`-shm` 이 모두 `0o600` 이었다(하네스 증거). `usage.db` 는 `services/usage_tracker.py` 모듈을
  import 하는 곳이 없어 서버가 열지 않는 유물 파일이므로 0644 로 남는다. 이 파일의 확인과 정리는 `[INFRA-079]` 범위다
- 결과: 통과 (쓰기로 열린 DB 는 모두 0600. 열리지 않는 `usage.db` 는 예상된 0644)
