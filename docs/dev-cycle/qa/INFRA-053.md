## 화면 대신 하네스를 쓰는 이유

`tier-rules.md` [3] 검증 3번이 「화면이 없는 경로는 해당 CLI·안전한 하네스를 검사 대상으로
삼고 그 사실을 적는다」고 정한다. 이 항목이 바꾸는 것은 파일 권한 비트와 그것을 유지하는
저장 함수이며, 화면에는 아무 변화가 없다.

**화면을 쓸 수 없는 이유가 하나 더 있다.** 설정 모달의 「저장」 버튼은 `POST /api/system/env`
를 통해 `update_env_file` 을 부르는데, 그것은 **운영 `.env` 를 실제로 고친다.** 이번 라운드의
안전 제약이 운영 파일에 쓰지 않는 것이므로 그 경로를 태울 수 없다. 대신 같은 함수를 임시
디렉터리의 사본에 대해 부른다. 검사하는 코드 경로는 동일하다.

**떠 있는 워커는 옛 코드를 들고 있다.** gunicorn 이 `--reload` 없이 기동하며, 5501 의 워커
셋은 `2026-09-08 00:39:54` 에 떴고 `services/common_env_service.py` 는 `07:37:58` 에 바뀌었다.
따라서 지금 화면에서 저장하면 `os.fchmod` 가 없는 옛 코드가 돈다. 이 사실은 이 사이클의
결함이 아니라 배포 성질이며, 다음 재기동에서 해소된다. 저장소의 기존 learning
`gunicorn-needs-hup-before-qa` 가 같은 것을 적고 있다.

## 시나리오

### S-1. 0644 인 `.env` 에 값을 저장하면 0600 이 된다 (회귀)
- 조작: 임시 디렉터리에 `.env` 를 만들고 `chmod 644` 한 뒤, `update_env_file` 로
  `OPENAI_API_KEY` 를 바꾼다.
- 기대: 최종 모드가 `0o600` 이고 파일 내용이 `OPENAI_API_KEY=new-value` 로 바뀌어 있다.
  모드만 재면 쓰기가 실패해도 통과하므로 내용을 함께 본다.
- 필수 여부(required): 예
- 실제: 모드 `0o600`, 내용 일치.
- 결과: 통과
- 증거: `pytest tests/app/test_common_env_service.py::test_update_env_file_narrows_file_mode`
- 정리(cleanup): `tmp_path` 픽스처가 회수한다

### S-2. 모드를 좁히는 시점에 파일이 비어 있다 (회귀)
- 조작: `os.fchmod` 를 스파이로 감싸 호출 시점의 파일 크기를 기록하고 같은 저장을 태운다.
- 기대: 기록된 크기 목록이 정확히 `[0]` 이다. 빈 목록이면 좁히기를 아예 부르지 않은 것이고,
  0 이 아니면 값이 쓰인 뒤에 좁힌 것이다. 둘 다 새 시크릿이 0644 아래 놓이는 창을 되살린다.
- 필수 여부(required): 예
- 실제: `[0]`. 최종 모드도 `0o600`.
- 결과: 통과
- 증거: `pytest ...::test_update_env_file_narrows_mode_before_writing`. 사본에 돌연변이 둘
  (`os.chmod` 로 되돌리기, 쓰기 뒤로 순서 바꾸기)을 넣으니 이 검사만 실패하고 나머지 여덟은
  통과했다. 즉 이 회귀를 잡는 검사는 이것 하나뿐이다.
- 정리(cleanup): 돌연변이 사본 디렉터리를 삭제했다

### S-3. 운영 `.env` 계열 파일이 0600 이고 `.env.example` 만 0644 다 (회귀)
- 조작: `ls -la .env .env.production .env.example .env.bak.* .env.production.bak.*`
- 기대: `.env`, `.env.production`, `.env.bak.*` 넷, `.env.production.bak.*` 하나가
  `-rw-------` 이고 `.env.example` 만 `-rw-r--r--` 이다. `.env.example` 은 추적되는 공개
  파일이라 좁히지 않는다.
- 필수 여부(required): 예
- 실제: 일곱 개가 `-rw-------`, `.env.example` 이 `-rw-r--r--`. mtime 은 전부 사이클 전과 같다.
- 결과: 통과
- 증거: 아래 실행 결과의 S-3 출력
- 정리(cleanup): 없음

### S-4. `.env` 를 새로 만드는 스크립트 경로가 0600 을 남긴다 (회귀)
- 조작: 임시 디렉터리에서 `scripts/init_all.sh:103-106` 의 두 줄
  (`cp .env.example .env` 와 `chmod 600 .env`)을 그대로 실행한다. 스크립트 전체는 venv 생성과
  `nano` 열기를 포함해 대화형이라 돌리지 않는다.
- 기대: 만들어진 `.env` 의 모드가 `600` 이다. `cp` 만 실행하면 umask 022 를 따라 `644` 다.
- 필수 여부(required): 예
- 실제: `cp` 만 하면 `644`, `chmod` 까지 하면 `600`.
- 결과: 통과
- 증거: 아래 실행 결과의 S-4 출력
- 정리(cleanup): 임시 디렉터리 삭제

### S-5. 좁힌 모드로 세 로더가 모두 읽는다 (인접)
- 조작: python-dotenv, `@next/env`, `scripts/env_value.sh` 로 각각 `.env` 를 읽는다. 값은
  출력하지 않고 키 개수와 길이만 본다.
- 기대: python-dotenv 가 0 이 아닌 키 개수를 내고, `@next/env` 가 키를 채우며,
  `env_value FLASK_PORT` 가 빈 값이 아니다. 읽기 권한이 없으면 0 이나 빈 값이 된다.
- 필수 여부(required): 예
- 실제: python-dotenv 57키, `.env.production` 59키, `@next/env` 58키,
  `env_value FLASK_PORT` 가 네 자리 숫자를 냈다.
- 결과: 통과
- 증거: 아래 실행 결과의 S-5 출력
- 정리(cleanup): 없음

### S-6. 이미 떠 있는 두 서비스가 계속 응답한다 (인접)
- 조작: `chmod` 뒤 `GET /health`(5501)와 `GET /`(3500)를 부른다. **재기동하지 않는다.**
- 기대: 둘 다 200. `chmod` 는 열린 파일 기술자나 이미 읽은 값을 건드리지 않는다.
- 필수 여부(required): 예
- 실제: `flask=200`, `next=200`.
- 결과: 통과
- 증거: 아래 실행 결과의 S-6 출력
- 정리(cleanup): 없음

### S-7. 다른 쓰기 경로도 0600 을 남긴다 (인접)
- 조작: 임시 디렉터리의 0644 `.env` 에 `persist_market_gate_interval_to_env` 를 태운다.
- 기대: 최종 모드가 `0o600` 이다. 이 경로는 `atomic_write_text` 를 쓰고 그 안의
  `NamedTemporaryFile` 이 0600 을 만들어 `os.replace` 가 그 모드째 옮기므로, 고치지 않아도
  이미 좁힌다. 이 시나리오는 그 전제가 참임을 확인해 「고치지 않은 결정」을 뒷받침한다.
- 필수 여부(required): 예
- 실제: `0o600`.
- 결과: 통과
- 증거: 아래 실행 결과의 S-7 출력
- 정리(cleanup): 임시 디렉터리 삭제

### S-8. 버려진 입력만 왔을 때 빈 `.env` 를 만들지 않는다 (인접)
- 조작: 파일이 없는 상태에서 `EDITABLE_ENV_KEYS` 밖의 키(`ADMIN_API_TOKEN`)만 넘긴다.
- 기대: 파일이 생기지 않는다. 이른 반환 둘 가운데 하나라도 사라지면 `open(w)` 가 빈 파일을
  만든다.
- 필수 여부(required): 예
- 실제: 파일 없음.
- 결과: 통과
- 증거: `pytest ...::test_update_env_file_does_not_create_file_when_nothing_to_write`
- 정리(cleanup): `tmp_path` 픽스처가 회수한다

### S-9. Turbopack 캐시를 다른 계정이 순회하지 못한다 (리포트)
- 조작: `frontend/.next` 의 디렉터리 모드를 확인하고, 그 아래 파일에 `.env` 값이 남아 있는지
  바이트 일치로 센다. 값은 출력하지 않고 키 이름과 개수만 본다.
- 기대: 디렉터리가 `drwx------` 이다. 하위 파일은 여전히 0644 이고 값도 남아 있지만, 순회가
  막히면 다른 uid 는 열 수 없다. 캐시는 실행마다 새로 만들어져 파일 모드로는 막을 수 없다.
- 필수 여부(required): 예
- 실제: `drwx------`. 차단 전 실측으로는 키 16개가 3,222개 파일에 평문으로 있었고 전부 0644,
  상위 디렉터리는 `drwxr-xr-x` 였다. `restart_all.sh` 에도 같은 한 줄을 넣어 다음 기동에서
  유지된다.
- 결과: 통과
- 증거: 아래 실행 결과의 S-9 출력
- 정리(cleanup): 없음

### S-10. 정적 검증 (인접)
- 조작: `pytest`, `npx vitest run`, `bash -n` 셋.
- 기대: 전부 종료 코드 0. pytest 는 이번에 더한 검사 셋을 포함해 1812건이다.
- 필수 여부(required): 예
- 실제: pytest 1812 통과·2 skip(exit 0). `bash -n` 은 `restart_all.sh`·`stop_all.sh`·
  `scripts/init_all.sh`·`scripts/env_value.sh` 넷 모두 0. vitest 는 **12회 실행 가운데 10회가
  335건 전부 통과했고 2회는 1건이 실패했다.**
- 결과: 통과. vitest 의 간헐 실패는 이번 변경과 무관하다고 판단했다. 근거는 셋이다. ① 두
  번의 실패는 모두 다른 명령이 같은 셸에서 동시에 돌던 때였고, 단독으로 연달아 돌린 6회는
  전부 통과했다. ② `tests/smoke/upgrade-smoke.test.ts:57` 의 `Build Verification` 이 실제로
  `next build` 를 돌려(4.8초) 파일 시스템 경합에 민감하다. ③ 이번 변경은 `frontend/` 아래
  소스를 한 줄도 건드리지 않는다. 바뀐 것은 `frontend/.next` 디렉터리의 모드뿐이고 그 모드는
  `next build` 를 여러 번 돌린 뒤에도 `drwx------` 로 유지된다.
- 미해결: **실패한 검사의 이름을 끝내 확보하지 못했다.** 재현되는 순간의 전체 출력을 남기려
  6회를 반복했으나 그동안 실패가 나오지 않았다. 이 간헐성 자체는 `[FE-042]` 로 이월한다.
- 증거: 아래 실행 결과의 S-10 출력
- 정리(cleanup): 스크래치패드의 실행 로그 파일을 삭제했다

## 이월한 발견

리뷰 넷이 이번 범위 밖에서 찾은 것을 백로그로 올렸다.
