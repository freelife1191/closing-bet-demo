# 수집기 통합과 대량 수급 조회 설계

대상: INFRA-030, FLOW-014 · 기준 커밋: b4a0ae5 · 설계일: 2026-09-21

## 승인과 현재 단계

사용자는 직전 대화에서 제시한 「수집기 통합 → 대량 수급 조회 지연 개선」 두 항목의
구조 설계 방향에 `승인`이라고 응답했다. 이는 상세 설계 작성의 근거다.
이 문서는 architectural 경로의 검토용 설계이며, 문서 자체의 승인과 구현 계획 검토는
아직 받지 않았다. 제품 코드·의존성·실행 중인 서비스는 변경하지 않는다.

## 목표와 범위

비상용 프로젝트의 중복 구현을 줄이고 과거 날짜 스크리닝의 수급 조회 대기 시간을 줄인다.
두 항목은 순서대로 구현하며 격리 환경·회귀 검사·리뷰·UltraQA 실행 자산을 공유한다.
각 항목의 완료 판정과 변경 집계는 분리한다. 관련 없는 나머지 10개 항목은 포함하지 않는다.

INFRA-030은 공개 수집기 import를 유지하면서 KRX·Naver·News 구현 선택을 명확히 한다.
개인 수급의 실제 0과 자료 없음을 구분해 소비자까지 전달한다.
FLOW-014는 기존 수급 판정을 보존하면서 배치의 순차 대기와 동일 요청 반복을 줄인다.
수급 집계 서비스가 위험 경로이므로 두 항목의 공유 검토는 T3로 수행한다.

## 확인한 현재 구조

- `engine/collectors.py`는 `__path__`를 설정하고 KRX를 직접 정의한다.
  끝에서 Naver·News만 하위 모듈의 클래스로 재노출한다.
- 공개 KRX의 `get_supply_data(code, target_date=...)`는 명시한 과거 날짜에서
  pykrx를 우선하며 실패하면 해당 날짜로 자른 CSV 결과로 내려간다.
  `engine/collectors/krx_local_data_mixin.py`의 구현에는 같은 날짜 인자가 없다.
- 통합 5일 서비스는 외국인·기관만 전달한다. KRX·Naver는 정상 CSV 경로의 개인 수급을
  0으로 채우지만 pykrx 경로에서는 실제 개인 수급을 사용한다.
- `engine/screener.py`는 순차 분석 중 자료가 부족한 종목마다 참조 조회를 수행한다.
  참조 캐시는 성공만 보관하며 메모리 키에는 현재 data_dir가 포함되지 않는다.
- `frontend/src/app/dashboard/kr/closing-bet/page.tsx`는 개인 수급에 `|| 0`을 적용하므로
  백엔드만 수정해서는 자료 없음이 화면에 전달되지 않는다.

근거는 위 소스와 `services/investor_trend_5day_service.py`,
`services/kr_market_stock_detail_service.py`, `engine/models.py`의 텍스트 조사다.
원본 자료 및 외부 시세를 조회한 결과로 주장하지 않는다.

## 선택한 구조와 대안

선택: 현재 실행 계약을 보존하는 패키지 통합 후, 기존 종목별 참조 계산의 제한된 병렬 실행.
다른 KRX 클래스를 그대로 공개하는 방법은 과거 날짜와 캐시 정책이 달라 제외한다.
실패 캐시만 추가하는 방법은 최초 서로 다른 N개 조회를 줄이지 못해 단독 해법으로 쓰지 않는다.
시장 전체 순매수 API로 교체하는 방법은 일별 5거래일 자료·외국인 집계·누락 종목 의미까지
새로 맞춰야 하므로 이번에는 선택하지 않는다. 새 패키지는 추가하지 않는다.

## INFRA-030: 수집기와 개인 수급 계약

`engine/collectors/__init__.py`가 세 공개 클래스를 명시적으로 재노출한다.
KRX는 현재 실사용 메서드·생성자·과거 날짜·캐시/fallback 계약을 기준으로 기존 패키지의
KRX와 mixin에 통합한다. 동작 대조를 통과한 뒤 `engine/collectors.py`와 중복 구현을 제거한다.
`__path__` 조작 및 import 실패를 숨기는 대체 클래스 정의를 남기지 않는다.
Naver·News는 현재 사용하는 모듈형 구현을 유지한다.

KRX 이전 검증에는 상위 등락 종목, 종목명, 상세 정보, 차트, 최신 시장일, 수급,
config의 상대/절대 DATA_DIR와 SQLite 캐시 키를 포함한다. 이동에 따라 BASE_DIR가 달라져
저장 위치가 바뀌지 않게 한다. 테스트 monkeypatch 위치는 공개 실행 경로로 옮기되
기존 동작 단언을 제거해 통과시키지 않는다. 죽은 구현만 겨냥한 테스트는 근거를 남긴다.

개인 수급은 내부 5일 payload의 `individual: int | None`으로 전달한다.
동일 5거래일·동일 금액 단위의 유효한 값이 모두 있을 때 합산하며 실제 0은 0으로 유지한다.
열/날짜/값이 부족하거나 비유한 값이면 None이다. 부분합이나 외국인+기관의 역산으로 채우지 않는다.
기존 외국인·기관의 선택 정책과 점수 산식은 바꾸지 않는다.
개인 값이 없다는 이유만으로 정상 CSV 경로에 외부 조회를 추가하지 않는다.
현재 CSV 생산 경로는 date/ticker/foreign_buy/inst_buy만 생성하므로 이 경로의 개인 값은
자료 없음이 된다. 이번에는 CSV 수집 스키마를 확장하지 않는다. pykrx의 개인 열과 Toss의
기존 개인 일별 입력처럼 출처와 단위가 확인되는 자료만 실제 값으로 전달한다.

SupplyData의 개인 필드와 Naver·상세 API 소비자에도 같은 nullable 계약을 적용한다.
화면은 None을 `자료 없음`, 실제 0을 중립 0으로 표시하고 null에 부호/색상 계산을 적용하지 않는다.
Toss의 수량 기반 일별 자료와 가격을 곱한 금액을 혼용하지 않으며, 기존 금액 변환을 유지한다.
캐시 직렬화/역직렬화도 개인 값과 가용성을 보존한다. 가용성 정보 없는 구형 캐시의 개인 값은
검증된 값으로 간주하지 않는다. 외국인·기관은 기존대로 읽고 개인만 자료 없음으로 처리한다.
원본 파일 일괄 재작성은 하지 않으며 새 캐시 형식은 버전으로 구분한다.

## FLOW-014: 대기·중복 조회 정책

과거 날짜 대량 스크리닝의 참조 조회만 최대 4개 동시 실행으로 바꾼다.
표준 라이브러리의 제한된 executor를 배치 실행 안에서 소유하고 종료 시 회수한다.
전체 종목 분석·Market Gate·LLM·파일 저장을 병렬화하지 않는다.
결과는 후보의 원래 순서로 소비하며 max_stocks, 대상 날짜, 점수와 순위를 보존한다.
먼저 prioritized_stocks의 첫 max_stocks행을 확정하고 그 안에서만 준비·조회한다.
가격 자료 부족으로 빈자리가 생겨도 cutoff 뒤 후보로 채우지 않는다.

기존 가격 자료 부족 등으로 수급 계산 전에 반환한 종목은 참조를 미리 조회하지 않는다.
현재는 VCP 판정이 false여도 수급을 계산하므로 새 패턴 필터를 추가하지 않는다.
기존 적격 판정을 재사용해 실제 수급이 필요한 후보만 최대 4개씩 준비한다.
CSV trend map은 제출 전에 주 실행 흐름에서 준비하고 읽기 전용 결과를 전달한다.
병렬 작업에서 공유 pandas 객체를 정규화·정렬·변경하지 않는다.
정상 CSV 종목에는 참조 호출 0회를 유지한다. 배치에서 받은 결과는 바로 소비하여
실패 결과가 소비 단계에서 다시 조회되지 않도록 한다.
이 제한은 실행 하나의 동시성이다. 별도 프로세스의 여러 배치를 전역 제한한다는 의미는 아니다.

동일 프로세스의 동일 참조 키 요청은 진행 중 조회를 공유한다. 키는 정규화된 data_dir,
provider, ticker, 날짜/최신 슬롯을 모두 포함한다. 다른 경로·날짜·provider를 섞지 않는다.
성공 캐시의 기존 정책은 유지하고, 빈 응답·예외는 완료 시점부터 monotonic 기준 60초만
메모리에 보관한다. 실패 캐시는 최대 4096개, 디스크에는 저장하지 않는다.
60초 후에는 재시도하며 clear 함수는 성공·실패 캐시를 함께 비운다.
네트워크 작업 중 전역 캐시 잠금을 잡지 않고, 예외에서도 대기자를 해제한다.
clear 이전에 시작한 작업은 기존 호출자에게 결과를 돌려줄 수 있지만 clear 이후 캐시를
다시 채우거나 새 요청의 공유 작업으로 선택되면 안 된다. 세대값으로 두 실행을 구분한다.
이 제한은 성공·실패 메모리와 SQLite publish 모두에 적용하며, 세대 확인과 publish를
clear에 대해 직렬화한다. 이미 저장돼 있던 성공 SQLite 자료를 삭제하는 기능은 추가하지 않는다.

첫 N개 서로 다른 종목의 네트워크 호출 수는 여전히 N개일 수 있다.
병렬 실행은 대기 시간을 줄이고, 키 공유와 실패 TTL은 중복 호출 수를 줄인다.
이를 「최초 조회 수 자체를 상수로 줄였다」고 보고하지 않는다.

HTTP 상세 조회에 새로운 전체 시간 예산은 이번에 넣지 않는다.
현재 pykrx 호출에는 저장소가 제어하는 전체 deadline이 없고 future timeout만으로는
기저 요청이 중단되지 않는다. 백그라운드 작업을 남기면서 timeout이라고 보고하지 않는다.
단일 조회는 기존 공급자 timeout/fallback을 유지하고 60초 실패 캐시의 효과만 받는다.
이는 FLOW-014의 시간 예산 도입 검토에 대한 보류 결정이며 무한 지연을 해결했다는 주장은 하지 않는다.

## 검증과 완료 기준

| 영역 | 필수 확인 |
|---|---|
| import | 공개 경로와 하위 경로가 같은 클래스를 반환, 레거시 파일/조작 제거, 순환 import 없음 |
| KRX | 기존 최신/과거 날짜, 캐시 적중·실패, 상대 DATA_DIR 계약의 전후 동등성 |
| 개인 수급 | 양수·음수·실제0·열 없음·부분5일·비유한 값·구형 캐시의 내부/API/UI 일치 |
| 배치 | 정상 CSV 외부0회, 부분누락 대상만 조회, cutoff 안의 가격부족 후보가 있어도 cutoff 밖 호출0회, 결과 순서 보존 |
| 경합 | 같은 키1회, 경로/날짜/provider 분리, 실패 후 대기자 해제, clear 전 작업의 메모리/SQLite 재삽입0회, 만료 후 재시도 |
| 성능 | 합성 600후보, 참조마다 고정 지연50ms에서 순차 대비3회 중앙값50% 이하, 최대 동시4 |
| 정확성 | 같은 합성 자료의 순차/개선 실행에서 결과·점수·순위 같음, 정상/결측 혼합 자료 포함 |
| 브라우저 | 실제 종목 상세 화면의 개인 수급0/양수/음수/자료 없음, 날짜별 자료와 오류복구 |

성능 수치는 외부 네트워크 속도 추정과 분리한다. 합성 지연 조건, API 호출 수, 소요 시간,
동시성 최대값을 보존한다. 외부 장애가 오래 지속될 때의 총시간 상한은 이 기준에 포함하지 않는다.

기존 기준 코드로 격리 baseline을 먼저 확인하고 회귀 검사를 만든 뒤 구현한다.
리뷰는 ponytail → code-review → T3 심층 리뷰 순서이며 지적 수정 후 영향 범위를 재검증한다.
전체 pytest, Vitest, typecheck, lint, build 및 UltraQA App 대응 필수 행렬을 수행한다.
브라우저는 사용자 지정 ego-browser로 실제 앱 UI와 실제 수정 서비스를 합성 공급자에 연결한다.
스크린샷 직접 열람, 요청/응답 상태, 콘솔/Next 진단과 소유 자원 정리를 완료 조건에 포함한다.

원본3500/5501/live는 접근·재시작하지 않는다. 실제 .env 및 data 내용을 읽거나 복사하지 않는다.
검증은 비밀 없는 소유 scratch에서 수행하며 dotenv·외부 통신·원본 쓰기를 차단한다.
실제 인증·LLM·수집·설정저장·거래·충전·삭제는 실행하지 않는다.
사용자 root package.json은 보존한다. OMX 런타임 활성화·상태 변경 없이 App 대응으로 기록한다.

## 예상 변경 경계와 후속 단계

수집기 패키지, engine/models.py, engine/screener.py와 수급 준비 헬퍼,
services/investor_trend_5day_service.py, 상세 API 서비스, 종가 상세 UI/타입 및 관련 검사다.
정확한 파일 배정과 커밋·QA 행렬은 이 문서 승인 후 writing-plans에서 작성한다.
프론트엔드 수정 전에는 frontend-skills 매핑과 Next 번들 문서를 읽는다.
두 항목은 공유 검증을 통과한 뒤 개별 완료 기록을 남긴다. 미통과 항목은 백로그에 유지한다.

## 설계 검토 기록

2026-09-21 자체 검토에서 VCP false 후보도 수급을 계산하는 기존 동작과
공유 pandas 객체를 수정하지 않는 병렬 경계를 명시했다.
독립 native critic은 max_stocks cutoff 밖 후보 조회 가능성과 clear 이후 SQLite 재삽입
가능성을 지적했다. 두 계약 및 검증 행을 보완한 뒤 최종 `OKAY`를 받았다.
이는 설계 문서 검토 결과이며 제품 테스트나 사용자 문서 승인을 대체하지 않는다.
