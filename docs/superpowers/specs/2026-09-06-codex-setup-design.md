# Codex 개발 사이클 연결 설계

2026-09-06 대화에서 제시한 저장소 연결 방식을 사용자가 승인했다.
작업 근거와 설치 절차는 `docs/dev-cycle/codex-setup.md` 이다.

## 목표와 범위

기존 개발 사이클과 감사 역할을 Codex에서 같은 이름으로 찾도록 연결한다.
절차의 정본은 `.claude/skills/dev-cycle/`, 역할의 정본은
`.claude/agents/dev-workflow.md` 에 유지한다. 이번 작업은 지정된 환경 설정이며
개발 백로그 항목을 실행하거나 카테고리 감사를 시작하는 사이클이 아니다.

## 확인한 환경

- 저장소 브랜치는 `develop` 이고 시작 시 작업 트리는 깨끗하다.
- Codex CLI 0.153.4, OMX 0.21.3, agent-browser 0.31.1이 설치되어 있다.
- QA·리뷰·계획·프론트엔드 스킬은 현재 세션 목록에 있다.
- gstack browse 실행 파일과 Next.js 번들 문서가 있다.
- 저장소의 `dev-cycle` 링크와 `dev-workflow` TOML 정의는 아직 없다.
- 현재 Codex App은 tmux 밖에서 실행 중이다. CLI 설치 상태와 현재 App의
  호출 가능 목록은 별도로 검증해야 한다.

## 선택한 구조

`.agents/skills/dev-cycle` 은 `../../.claude/skills/dev-cycle` 을 가리키는
상대 심볼릭 링크다. 원본의 frontmatter와 참조 파일을 그대로 사용하며 복제하지 않는다.

`.codex/agents/dev-workflow.toml` 은 이름·설명·읽기 전용 설정과 원본을 읽으라는
지시만 담는다. 모델과 추론 수준은 별도로 지정하지 않는다. 역할 본문의 단일 카테고리
제약을 따르되, 설치 검증에서는 「하지 않을 일」만 반환하고 감사를 시작하지 않는다.

Codex 호출 안내는 사이클 스킬의 실행 환경 표에 모은다. 진입 문서와 감사 역할 문서,
티어 규칙과 프론트엔드 참조 문서는 이 표와 일치시킨다. `CLAUDE.md` 의 공통 규범과
티어·검증 범위는 유지한다. 설정 안내에 설치 파일과 실제 호출의 검증 결과를 구분해 남긴다.

## 대안과 선택 이유

홈 디렉터리마다 정의를 복제하면 기기별 수정이 갈라진다. 문서를 직접 읽는 현재 방식은
대체 수단으로 유지할 수 있지만 이름으로 찾는 목표를 충족하지 못한다. 저장소의 링크와
얇은 역할 정의를 선택하면 정본을 유지하면서 연결 자체를 버전 관리할 수 있다.

## 실패 처리와 제약

- 기존 경로가 있으면 먼저 확인하고 다른 대상의 링크나 정의를 덮어쓰지 않는다.
- 홈 디렉터리의 기존 스킬·에이전트·설정을 변경하지 않는다. 새 의존성은 추가하지 않는다.
- 애플리케이션 서버·LLM·데이터 갱신 API를 호출하지 않는다.
- `.env` 와 `data/` 는 접근하지 않는다. `~/.claude/` 는 읽지 않고
  `~/.agents/skills` 는 디렉터리 목록만 확인한다.
- 새 역할이 현재 App에 노출되지 않으면 등록 성공으로 기록하지 않는다. 허용된 일반
  서브에이전트에 역할 파일 경로를 주는 검증은 원본 참조 확인으로만 보고한다.
- 스킬 목록에 새 링크가 노출되지 않으면 링크의 파일을 직접 읽어 `[S] status` 를
  수행한다. 이는 `$dev-cycle` 자동 탐색과 별개의 검증이다.

## 완료 기준

링크가 정본에 도달하고 TOML이 정상적으로 파싱되어야 한다. 필요한 도구의 존재,
문서 참조와 호출 안내의 일관성, 상태 브리핑을 확인한다. 역할 호출의 성공 또는 환경상
한계를 실제 결과로 기록한다. 변경은 설정과 문서로 제한하며 `git diff --check` 를
통과한 뒤 설정 절차가 정한 한 커밋으로 남긴다. 다음 백로그 사이클은 시작하지 않는다.
