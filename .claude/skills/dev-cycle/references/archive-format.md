# TODO 및 아카이브 기록 형식

dev-cycle 이 백로그와 완료 기록을 남기는 형식이다. 형식을 바꾸려면 이 파일만 고친다.

## 1. 파일 위치

```
docs/dev-cycle/
  TODO.md                    백로그. 대기 중이거나 진행 중인 항목만 담는다
  qa/
    FLOW-010.md              항목별 QA 시나리오와 실행 결과. 형식은 §8
  archive/
    2026-09.md               월별 요약. 완료 항목을 한 줄씩 적는다
    daily/
      2026-09-01.md          일별 상세. 완료 항목의 전체 기록
```

백로그는 `TODO.md` 한 곳에만 둔다. CLAUDE.md 를 비롯한 다른 문서에 할 일 목록을 중복해서
적지 않는다. 중복된 백로그는 반드시 어긋난다.

## 2. 항목 ID

`<카테고리 약어>-<세 자리 일련번호>` 형식을 쓴다.

| 약어 | 카테고리 | 주요 경로 |
|---|---|---|
| `CHAT` | 챗봇 | `chatbot/`, `app/routes/kr_market_chatbot_*`, `frontend/src/app/chatbot/` |
| `JONGGA` | 종가베팅 | `app/routes/kr_market_jongga_*`, `frontend/src/app/dashboard/kr/closing-bet/` |
| `VCP` | VCP 시그널 | `engine/vcp_ai_analyzer*`, `app/routes/kr_market_vcp_*`, `services/kr_market_vcp_*`, `frontend/src/app/dashboard/kr/vcp/` |
| `FLOW` | 수급·백테스트 | `services/investor_trend*`, `services/kr_market_backtest_*`, `services/kr_market_flow_service.py`, `frontend/src/app/dashboard/kr/cumulative/` |
| `FE` | 프론트엔드 공통 | `frontend/src/app/components/`, `frontend/src/lib/`, `frontend/src/app/dashboard/kr/page.tsx` |
| `INFRA` | 인프라·패키지 | `requirements.txt`, `frontend/package.json`, `services/scheduler*`, `scripts/init_data.py`, `frontend/src/app/dashboard/data-status/` |

대시보드 화면 세 개는 담당 API 로 갈랐다. `dashboard/kr/` 홈은 백테스트 요약과 갱신
설정을 얕게 걸칠 뿐 특정 기능에 속하지 않아 `FE` 다. `cumulative/` 는
`/api/kr/closing-bet/cumulative` 하나만 부르므로 백테스트를 이미 담당하는 `FLOW` 이고,
`data-status/` 는 `/api/system/*` 과 수집 갱신 제어를 부르므로 스케줄러를 담당하는
`INFRA` 다. 한 항목이 여러 경로를 건드리면 주된 대상이 있는 카테고리를 쓴다.

일련번호는 카테고리별로 독립 증가하며 완료 후에도 재사용하지 않는다. 다음 번호는
`TODO.md` 와 `archive/` 전체에서 해당 약어의 최대 번호에 1을 더해 정한다.

```bash
# CHAT 카테고리의 다음 번호를 구한다
grep -rhoE 'CHAT-[0-9]{3}' docs/dev-cycle/ | sort -u | tail -1
```

## 3. 우선순위

| 값 | 뜻 |
|---|---|
| `P0` | 즉시 처리한다. 동작이 깨져 있거나 다른 작업을 막고 있다 |
| `P1` | 이번 주기에 처리한다 |
| `P2` | 대기한다. 순서가 오면 처리한다 |

## 4. TODO.md 형식

```markdown
# TODO

> 백로그의 단일 관리 지점입니다. 형식은
> `.claude/skills/dev-cycle/references/archive-format.md` 를 따릅니다.
> 최종 필수 QA가 통과한 완료 항목만 아카이브로 옮기고 이 파일에서 제거합니다.

## P0 — 즉시

### [INFRA-001] 파이썬 의존성 버전 고정
- 카테고리: 인프라 | 티어: T3 | 근거: AUDIT-INFRA §1
- 설계 승인: 승인 일자 2026-09-06 | 승인 확인 시각 2026-09-06 14:32
  | 범위: `requirements.txt` 핀과 Gemini 2.x 호환 경로
  | 실제 대화 근거: 2026-09-06 사용자 「진행해」 응답, 현재 세션의 해당 설계 제안
- QA 시나리오: 챗봇에 질문을 보내면 답변이 스트리밍으로 도착한다
- [ ] requirements.txt 에 버전 핀 적용
- [ ] google-genai 2.x 호환성 확인
- [ ] 회귀 테스트 확인

## P1 — 이번 주기

### [VCP-001] ...

## P2 — 대기

### [FE-001] ...
```

각 항목은 제목 줄, 카테고리·티어 메타 줄, 새 개발 라운드라면 `설계 승인` 메타 줄, 선택적인
`QA 시나리오` 줄, 체크박스 목록으로 이루어진다. 카테고리와 티어는 반드시 적고, 감사에서
나온 항목이면 근거를 함께 적는다. 근거는 감사 리포트의 절 번호를 가리킨다.

새 개발 라운드의 `설계 승인` 줄에는 승인 시각, 승인한 범위, 실제 대화의 근거를 함께 적는다.
실제 승인 시각을 알 수 없으면 `승인 일자`와 `승인 확인 시각`을 분리해 적고, 확인 시각을
승인 시각처럼 꾸며 쓰지 않는다. 재개와 QA 재시도는 같은 승인 범위를 이어 쓰므로 기존 기록을
가리킨다. 설계 문서에 적힌 `승인됨` 같은 주장만으로는 승인 근거가 아니다. 사용자의 실제
응답이나 그 응답을 포함한 세션 기록처럼 출처를 대조할 수 있는 근거를 적는다.

`QA 시나리오` 줄에는 그 항목이 **화면에서 무엇을 확인하면 고쳐졌다고 말할 수 있는지**를 한
줄로 적는다. `SKILL.md` [3] 검증 4번은 이 줄에서 출발해 §8의 시나리오 문서를 만든다.
화면에서 확인할 것이 없는 항목이면 줄 자체를 뺀다.

체크박스는 실행 단위를 적는다. 세 개에서 여섯 개 사이가 적당하며, 열 개를 넘으면 항목을
둘로 쪼갠다.

## 5. 일별 상세 형식

`docs/dev-cycle/archive/daily/YYYY-MM-DD.md` 에 완료 순서대로 덧붙인다. 파일이 없으면
그날 첫 완료 시점에 다음 헤더로 새로 만든다.

```markdown
# 2026-09-01

## [INFRA-001] 파이썬 의존성 버전 고정
- 완료 2026-09-01 14:32 | 티어 T3 | 커밋 abc1234, def5678
- 변경: requirements.txt, engine/genai_client.py (+42 -18)
- 리뷰: next 번들 문서 05-server-and-client-components(RSC 경계 확인) · ponytail-review(net -12) · code-review(3건 적용)
- 검증: pytest 1515 통과 · vitest 160 통과 · QA 시나리오 7/7 통과 (헬스 99)
- 메모: google-genai 2.x 에서 GenerateContentConfig 시그니처가 바뀌어 대응했다
```

- **완료** 줄에는 시각, 티어, 커밋 해시를 적는다. 커밋이 여럿이면 쉼표로 잇는다.
  QA 실행 단계가 시나리오 실패를 고치며 만든 커밋도 이 사이클의 커밋이므로 함께 적는다.
  빠뜨리면 그 수정이 어느 사이클에서 나왔는지 추적할 수 없다. 아카이브 커밋 자신은
  해시를 알 수 없으므로 적지 않는다.
- **변경** 줄에는 건드린 파일과 `git diff --stat` 의 증감을 적는다. 파일이 다섯 개를
  넘으면 대표 파일 세 개와 `외 N개` 로 줄인다.
- **리뷰** 줄에는 이 사이클에서 실제로 읽거나 돌린 스킬과 에이전트를 모두 적는다.
  `tier-rules.md` §1 표의 리뷰 열에 있는 것뿐 아니라 `SKILL.md` [1] 설계와 계획 3번에서
  고르고 [2] 구현에서
  읽은 스킬도 함께 적는다. 각 자산 뒤 괄호 안에 결과를 요약하고, 구현 스킬은 그 스킬이
  실제로 바꾼 판단을 적는다. 바꾼 것이 없으면 `(해당 없음)` 이라고 적어 읽었다는 사실만
  남긴다.

  이 줄이 기록의 전부다. 다음 사이클은 아카이브를 읽고 무엇이 관행인지 판단하는데,
  기록되지 않은 자산은 쓰지 않아도 되는 것으로 읽힌다. 2026-09-04 시점에 프론트엔드를
  건드린 사이클이 17건이었는데 배정된 스킬이 기록된 것은 한 건뿐이었고, 원인이 이
  자리였다. 종전에는 "실제로 돌린 자산만 적는다. 티어가 T1 이면 `ponytail-review` 하나만
  적힌다" 고 되어 있어서 리뷰 열 밖의 자산은 적을 자리가 없었다.
- **검증** 줄에는 실행한 테스트와 그 결과를 적는다. 완료 아카이브의 QA 시나리오는
  `통과/전체` 형태이며 반드시 전체 통과다. 실패했다가 같은 사이클에서 고쳐 다시 통과한
  시나리오는 `QA 시나리오 7/7 통과 (S-4 실패 → 고침)`처럼 괄호로 남긴다. 필수 QA가
  실패·차단·미실행이면 완료 아카이브를 만들 수 없고 TODO 항목을 유지한다. 과거 아카이브의
  `실패 → 이월` 표기는 읽기 호환을 위해 보존하며 소급 수정하지 않는다.
- **메모** 줄은 다음에 같은 자리를 건드릴 사람이 알아야 할 사실이 있을 때만 적는다.
  없으면 줄 자체를 뺀다.

## 6. 월별 요약 형식

`docs/dev-cycle/archive/YYYY-MM.md` 의 표에 한 줄을 덧붙이고 통계를 갱신한다. 파일이
없으면 그달 첫 완료 시점에 새로 만든다.

```markdown
# 2026-09 요약

| 완료일 | ID | 제목 | 카테고리 | 티어 | 커밋 |
|---|---|---|---|---|---|
| 09-01 | INFRA-001 | 파이썬 의존성 버전 고정 | 인프라 | T3 | abc1234 |

## 통계
- 완료 1건 (P0 1 · P1 0 · P2 0)
- 순 코드 증감 +24줄
```

통계는 항목을 추가할 때마다 다시 계산해서 덮어쓴다. 순 코드 증감은 그달 각 항목의
`변경` 줄에 적힌 증감을 합한 값이다.

## 7. 기록 시점

`SKILL.md` [3] 검증 5번에서 구현과 QA 시나리오 문서를 첫 커밋에 담되 TODO 항목은
유지한다. 6번 실행과 7번 결과 기록을 마친 뒤, 필수 QA의 최종 상태가 통과이고
결과·증거·정리가 모두 기록된 경우에만 [4] 마감 3번의 아카이브 커밋에 TODO 항목 제거와
아카이브 기록을 함께 담는다. 월말에 몰아서 집계하는 배치 작업은 두지 않는다.

## 8. QA 시나리오 문서 형식

`docs/dev-cycle/qa/<항목 ID>.md` 에 사이클마다 하나씩 만든다. `SKILL.md` [3] 검증 4번에서
계획을 기록하고, 5번의 첫 커밋으로 보존한 뒤, 6번 실행 결과와 7번의 결과·증거·정리를
같은 파일에 덧붙인다. 필수 실패·차단·미실행 또는 정리 미완료는 8번에 따라 TODO를 유지하며,
10번과 [4] 마감 3번의 완료 아카이브로 가지 않는다. 두 단계를 한 파일에 두는 이유는, 무엇을
검사하기로 했는지와 실제로 무엇이 나왔는지가 떨어져 있으면 나중에 대조할 수 없기 때문이다.

```markdown
# [FLOW-010] 등급별 성과 카드의 집계 원천 — QA 시나리오

- 대상 화면: http://localhost:<소유한 격리 포트>/dashboard/kr/cumulative
- 구성 근거: /qa-only 리포트 (.gstack/qa-reports/qa-report-localhost-3500-2026-09-03.md)
  + 이번 사이클의 변경 세 파일
- 구성 2026-09-03 09:14 | 실행 2026-09-03 09:41
- QA 엔진(engine): Claude Code `/qa-only` → `/qa`
- 단계(phase): 시나리오 구성 완료 | 실행 완료
- 반복(iteration): 1회
- baseline 상태: 기준값 수집 완료
- 필수 여부(required): 예
- 결과: 통과
- 증거: `.gstack/qa-reports/qa-report-localhost-3500-2026-09-03.md`
- 정리(cleanup): 임시 프로세스·fixture 없음

## 시나리오

### S-1. 페이지를 넘겨도 등급 카드가 고정된다 (회귀)
- 조작: 화면을 연 뒤 S·A·B 카드의 건수와 승률과 평균 수익률을 읽는다. 표 아래 `Next` 를
  눌러 2페이지로 넘어가 같은 세 값을 다시 읽는다.
- 기대: 두 페이지에서 S 는 `16건 / 37.5% / +0.3%`, A 는 `26건 / 48% / +1.6%`,
  B 는 `131건 / 37.2% / +0.2%` 로 완전히 같다.
- 필수 여부(required): 예
- 실제: 1·2페이지에서 위 S·A·B 값을 각각 읽어 일치했다.
- 결과: 통과
- 증거: `.gstack/qa-reports/qa-report-localhost-3500-2026-09-03.md`의 S-1 실행 로그
- 정리(cleanup): 이 시나리오가 소유한 임시 자료 없음

### S-2. 등급 필터 버튼은 현재 페이지를 센다 (인접)
- 조작: 1페이지와 2페이지에서 등급 필터 버튼의 괄호 안 숫자를 읽는다.
- 기대: 1페이지 `S (7) A (14) B (29)`, 2페이지 `S (3) A (4) B (43)`. 바로 위 결과 필터와
  같은 기준이므로 페이지마다 달라지는 것이 정상이다.
- 필수 여부(required): 예
- 실제: 1페이지와 2페이지에서 각각 기대한 버튼 수를 읽었다.
- 결과: 통과
- 증거: `.gstack/qa-reports/qa-report-localhost-3500-2026-09-03.md`의 S-2 실행 로그
- 정리(cleanup): 이 시나리오가 소유한 임시 자료 없음

### S-3. ...

## 이월한 발견

1단계 리포트가 지적했지만 이번 사이클에서 고칠 수 없어 백로그로 올린 것을 적는다.

- ISSUE-001 「누적 추천수 180 인데 표는 173행」 → `[FLOW-013]`. 백엔드 집계와 화면을
  함께 고쳐야 하고 D 등급을 어떻게 다룰지 정해야 해서 이번 범위를 넘는다.

## 실행 결과

- 필수 시나리오: 통과 8 / 전체 8
- 미통과 필수: 없음
- 재개 판정: 완료 가능
- 시나리오 밖에서 새로 발견: 없음
```

- **시나리오 번호**는 `S-1` 부터 붙이고 문서 안에서만 유일하면 된다.
- **분류**는 제목 끝 괄호에 `회귀` `인접` `리포트` 가운데 하나를 적는다. 근거는
  `tier-rules.md` §1-1 의 1단계에 있다.
- **기대**에는 눈으로 대조할 수 있는 값을 적는다. `정상 동작한다` 는 기대값이 아니다.
- **QA 메타데이터**에는 `engine`, `phase`, `iteration`, baseline 상태, 필수 여부, 결과,
  증거, `cleanup`을 모두 적는다. Codex는 `QA 엔진(engine): Codex UltraQA`와 함께
  `- UltraQA Report: <보고서의 Markdown 링크>`를 기록한다. 실제 Codex 절차는
  [references/ultraqa.md](ultraqa.md)를 따른다.
- **Codex 브라우저 기록**에는 `browser_applicability: required|not-applicable`와 호출부 근거,
  required이면 `browser_driver: agent-browser`와 전용 namespace/session·실제 진입 URL을,
  not-applicable이면 `browser_driver: none`과 UI가 없다는 근거를 적는다.
  웹 시나리오는 조작 전후 DOM/스냅샷·화면 기대값/실제값·요청/응답·스크린샷 확인·오류 판정과
  대역 적용 범위를 함께 남긴다. 실제 UI와 API 하네스의 결과를 합쳐 어느 쪽을 실행했는지
  숨기지 않는다. 필수 여부와 예외 판정은 ultraqa.md §1-1을 따른다.
- **시나리오별 기록**에는 `필수 여부(required)`, 실제 관측값, 결과, 증거, `cleanup`을
  모두 적는다. 문서 전체의 필수 여부만으로 각 시나리오의 필수 여부를 합산하지 않는다.
- **결과**는 실행 후에 채운다. 신규 시나리오별 결과는 `통과`, `실패 → 고침`, `실패`,
  `차단`, `미실행` 가운데 실제 상태로 적는다. `실패 → 고침`은 실제 재실행이 통과한 경우에만
  쓴다. 필수 시나리오가 실패·차단·미실행이면 그 상태와 증거를 문서에 보존하고 TODO를
  유지한다. 완료 아카이브를 만들지 않는다.
- **실행 결과**에는 필수 시나리오의 통과 수와 전체 수, `미통과 필수` 목록(시나리오 ID·상태·
  증거), 재개 판정을 적는다. 미통과 목록이 비어 있을 때만 `완료 가능`으로 적는다. 실행 뒤
  필수 시나리오를 optional로 낮춰 완료 조건을 우회하지 않는다.
- **이월한 발견**에는 시나리오 밖에서 발견해 백로그로 올린 항목 ID와 이월 사유만 적는다.
  이월할 것이 없으면 절 자체를 뺀다. 과거 문서의 `실패 → 이월`은 읽기 호환을 위해
  보존하되 소급 수정하지 않는다.
- 실제 비용이 드는 조작(LLM API 호출을 일으키는 `실패 AI 재분석`, `Refresh VCP` 등)은
  시나리오에 넣지 않는다. 사용자가 그 지출을 승인한 자리가 아니다.
